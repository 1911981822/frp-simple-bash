# frp 二次封装项目需求文档

- **文档版本**：V0.1
- **文档状态**：需求基线草案
- **编写日期**：2026-11-09
- **产品形态**：跨平台安装脚本 + 终端交互式管理命令
- **目标平台**：主流 Linux 发行版、Windows x64

---

## 1. 项目背景

frp 是一套反向代理和内网穿透工具。本项目在官方 frps/frpc 二进制能力之上，提供一套面向终端用户的安装、配置、运行管理和映射管理封装，降低 frp 的部署与使用门槛。

用户无需手动编写复杂配置文件，即可通过一条安装命令完成安装，并通过 `frps` 或 `frpc` 命令进入数字菜单，完成服务启停、配置修改、服务端切换及端口映射管理。

---

## 2. 产品目标

### 2.1 总体目标

1. 使用 Bash 命令快速安装和管理 Linux 版本 frps/frpc。
2. 使用 PowerShell 安装和管理 Windows 版本 frps/frpc。
3. 自动配置后台运行、自启动和系统服务。
4. 首次安装通过向导逐步收集必要配置，减少手工编辑配置文件。
5. 通过 `frps`、`frpc` 命令提供统一、清晰、可恢复的终端菜单。
6. 支持一个 frpc 保存多个 frps 服务端连接配置。
7. 不同 frps profile 的端口映射配置必须相互隔离。
8. 对 token、TLS、配置文件权限、危险端口和防火墙提供安全默认值。

### 2.2 非目标

以下内容不作为首期必须实现的范围：

- Web 管理面板。
- 同一台机器同时运行多个 frpc 实例。
- 自建 frp 服务端集群、负载均衡和高可用。
- 自动修改云厂商安全组规则。
- 自动打洞、自动申请域名或自动签发公网证书。
- 复杂的 STCP、SUDP、XTCP 等高级代理类型。

---

## 3. 目标用户与使用场景

### 3.1 目标用户

- 需要部署 frps 服务端的 Linux/Windows 管理员。
- 需要通过 frpc 暴露内网服务的个人或小型团队。
- 不熟悉 TOML 配置文件、systemd 或 Windows Service 的用户。
- 需要管理多个 frps 服务器和不同端口映射的运维人员。

### 3.2 典型场景

1. 用户在公网 Linux 服务器执行安装命令，完成 frps 部署并设置开机启动。
2. 用户在内网 Linux 或 Windows 机器执行 frpc 安装命令，输入 frps 地址、端口和 token，完成首次连接。
3. 用户通过 `frpc` 菜单新增一个 frps profile，并在该 profile 下新增 TCP/UDP/HTTP/HTTPS 映射。
4. 用户切换到另一个 frps profile，查看或修改该服务端独立的映射配置。
5. 用户通过 `frps` 菜单查看当前在线客户端及其代理信息。

## 4. 支持平台与兼容性

### 4.1 Linux

首期支持以下系统族：

- Debian/Ubuntu
- CentOS/RHEL/Rocky Linux/AlmaLinux
- Alpine Linux
- 其他兼容 systemd 或 OpenRC 的 Linux 发行版

服务管理策略：

| 系统环境 | 首选服务管理方式 | 兼容方式 |
|---|---|---|
| systemd 系统 | systemd service | 后台进程模式 |
| Alpine/OpenRC | OpenRC service | 后台进程模式 |
| 无服务管理器 | 后台进程 | 明确提示无法保证自启动 |

CPU 架构应至少设计为可扩展支持 `amd64/x86_64`、`arm64/aarch64`，具体发布包以官方 frp Release 可用架构为准。

### 4.2 Windows

- 首期支持 Windows x64。
- 提供 PowerShell 安装脚本。
- 安装和注册服务时自动检测管理员权限；没有管理员权限时给出提权提示。
- 使用 Windows Service 实现后台运行和自启动。
- 同时提供 `frps.exe`、`frpc.exe` 及菜单入口脚本/命令。
- Windows 防火墙只做规则检测和提示，是否自动修改规则需通过明确确认。

### 4.3 frp 版本策略

- 首期固定使用官方 GitHub Releases 的 frp `v0.72.0`。
- 首期安装资产支持 `linux_amd64`、`linux_arm64` 和 `windows_amd64`。
- 安装器必须显示待安装版本、系统、架构和下载地址。
- 支持指定版本安装，但默认不在每次安装时自动追踪最新版本。
- 通过 `upgrade` 主动升级，升级前备份配置并提供回滚提示。
- 配置生成必须以 frp `v0.72.0` 的实际 TOML 配置格式为准，避免沿用已废弃字段。
- 首期代码仓库为 `https://github.com/1911981822/frp-simple-bash`，安装脚本使用 `main` 分支根目录中的固定脚本文件名。

## 5. 安装与初始化

## 5.1 服务端 frps 安装

Linux 示例入口：

```bash
bash -c "$(curl -fsSL https://<项目安装地址>/install-frps.sh)"
```

也应支持下载脚本后本地执行，以及指定版本、安装目录和镜像地址等参数。

Windows 示例入口：

```powershell
irm https://<项目安装地址>/install-frps.ps1 | iex
```

实际项目中应提供可审计的下载和本地执行方式，不强制用户盲目执行未经查看的远程脚本。

安装流程：

1. 检测操作系统、版本、CPU 架构和管理员权限。
2. 检测是否已安装 frps、已有服务及已有配置。
3. 询问或确认 frp 版本、下载源和安装目录。
4. 下载并校验二进制文件，建议支持 SHA256 校验。
5. 创建配置、数据、日志和备份目录。
6. 引导输入 frps 基础配置：绑定地址、监听端口、token、TLS 等。
7. 引导配置 Dashboard/API：监听地址、端口、用户名、密码。
8. 生成系统服务并设置是否开机启动。
9. 启动服务并执行健康检查。
10. 输出安装结果、配置路径、服务名称、日志查看方式和下一步命令。

### 5.2 客户端 frpc 安装

安装脚本完成基础安装后，首次运行配置向导。向导至少应逐步询问：

1. frp 版本、安装目录和服务名称。
2. 服务端名称，例如 `生产服务器`、`家庭服务器`。
3. 服务端 IP 或域名。
4. 服务端 frp bind 端口。
5. 是否启用 token 认证；若启用，输入 token。
6. 是否启用 TLS；若启用，询问相关 TLS 参数。
7. 是否需要保存为当前 active profile。
8. 是否立即启动 frpc 并设置开机自启动。
9. 是否立即新增第一条端口映射。

token 在终端输入时应支持隐藏显示，保存和展示时必须脱敏。TLS、用户名和密码类字段均为可选项，可以留空。需要注意：frp 客户端连接认证字段必须严格对应当前 frp 版本支持的认证机制；Dashboard 用户名/密码与 frpc 连接认证应分别建模，不能混用。

## 6. 命令入口与交互规范

### 6.1 命令入口

Linux：

```bash
frps
frpc
```

Windows：

```powershell
frps
frpc
```

Windows 内部可由 `frps.ps1`/`frpc.ps1` 或包装器调用对应的 exe。

### 6.2 通用菜单规范

- 用户在终端直接输入 `frps` 或 `frpc` 后，程序必须进入对应的交互式数字菜单。
- 菜单中的每个功能必须显示唯一的数字编号、功能名称和简短说明。
- 用户只需输入对应数字并按回车，即可执行该项操作；不要求用户输入复杂命令或记忆子命令。
- 数字菜单是首要、默认的使用方式，适用于安装后的日常管理操作。
- 输入无效数字、空输入或非预期字符时，不得退出程序；应提示可选范围并重新等待输入。
- 每次操作完成后显示成功结果、失败原因和下一步选项，并返回当前菜单或上一级菜单。
- 支持 `0` 返回上一级；在主菜单输入 `0` 返回或退出程序。可选支持 `q` 作为退出快捷键，但不能替代数字操作。
- 菜单应显示当前状态，例如运行中/已停止、当前版本、当前 profile 和连接状态，使用户在选择数字前了解上下文。
- 修改配置前显示当前值，并支持输入 `0` 或选择取消返回，不得因取消而修改配置。
- 修改会先进行格式和冲突校验，再写入临时文件；校验通过后才原子替换正式配置。
- 涉及重启、停止服务、删除配置、卸载或开放公网端口的操作，必须在执行前显示影响并要求再次确认。
- token、密码、私钥等敏感值默认脱敏；输入 token 或密码时应隐藏回显。
- 非交互参数模式作为自动化补充方式，至少支持：`status`、`start`、`stop`、`restart`、`install`、`uninstall`、`version`、`path`、`logs`、`upgrade`。
- 预留 `--json` 输出，供未来面板或自动化工具使用；非交互模式不得影响数字菜单的默认体验。

## 7. frps 服务端功能需求

### 7.1 状态与信息

`frps` 主菜单至少包含：

1. **运行状态**：运行中、已停止、异常、未安装；服务 PID、启动时间、最近退出原因。
2. **版本信息**：当前版本、安装来源、可用更新版本（如可检测）。
3. **路径信息**：二进制路径、主配置路径、服务文件路径、日志路径、备份路径。
4. **服务控制**：启动、停止、重启、设置/取消开机自启动。
5. **客户端连接信息**：通过 Dashboard/API 获取在线客户端、客户端名称/ID、连接时间、心跳状态、流量、代理数量和代理状态。
6. **配置查看与修改**：监听地址/端口、token、TLS、Dashboard/API 等。
7. **日志查看**：最近日志、持续跟踪、错误摘要。
8. **卸载**：停止服务、移除服务注册、删除二进制；默认保留配置和日志，可选择彻底清理。
9. **升级**：备份配置、下载新版本、校验、替换并重启；失败时恢复旧二进制。

### 7.2 客户端连接信息

- 首选通过 frps Dashboard/API 获取数据。
- Dashboard/API 默认不应无保护地暴露公网；默认绑定本机或用户明确指定的管理地址。
- 用户首次配置 Dashboard 时设置独立的管理用户名和密码。
- Dashboard 密码不可在菜单中明文回显。
- API 不可用时，应明确提示“无法获取实时客户端信息”，不能将过期缓存伪装成实时状态。
- 日志回退只作为辅助诊断，不作为完整在线状态的唯一来源。

### 7.3 服务端配置安全

- token 默认启用并强制最小长度校验。
- TLS 为可选安全项，但安装器应推荐启用。
- 管理端口与 frp 业务端口分离。
- 对常见危险端口、端口占用、监听 `0.0.0.0` 等情况给出警告。
- 配置文件权限按最小权限设置；Linux 至少限制为服务用户可读，Windows 使用受限 ACL。

## 8. frpc 客户端功能需求

### 8.1 主菜单

`frpc` 主菜单至少包含：

1. 当前 frpc 运行状态。
2. 当前使用的 frps 服务端名称、地址、端口。
3. 当前连接状态：已连接、连接中、断开、认证失败、配置错误。
4. 当前客户端版本、二进制路径、配置路径和服务状态。
5. 启动客户端。
6. 停止客户端。
7. 重启客户端。
8. 设置/取消开机自启动。
9. 新建 frps 服务端 profile。
10. 查看全部 frps profile。
11. 切换当前 frps profile。
12. 修改当前 frps profile。
13. 删除 frps profile。
14. 进入“修改当前 frps（服务端别名）端口映射”子菜单。
15. 查看日志和连接诊断。
16. 更新、卸载和配置备份。

其中，第 14 项必须显示当前服务端别名，例如“修改当前 frps（生产服务器）端口映射”，并进入端口映射专用子菜单。新增、查看、修改、启用/停用和删除映射均不得直接作为主菜单平级功能。

### 8.2 多服务端 profile

首期采用“保存多个服务端配置，运行一个 frpc 实例”的模式：

- 一个 profile 代表一台 frps 服务端。
- 新建 profile 时必须设置服务端名称，例如“生产服务器”。
- 服务端名称允许使用中文、字母、数字以及常见连接字符 `-`、`_` 的组合；不允许包含空格，尤其不允许名称中间出现空格；其他特殊字符默认不允许。
- profile 至少包含：唯一 ID、唯一显示名称、地址、frps bind 端口、Dashboard/API 管理端口、认证配置、TLS 配置、创建时间、更新时间和启用状态。
- 服务端名称、地址和端口在菜单中组合显示，例如：`生产服务器（192.0.2.10:7000）`。
- 服务端名称必须唯一；如果名称重复，应提示用户重新输入，不自动覆盖已有 profile。
- 用户可以修改已创建 profile 的服务端名称；修改名称前应校验格式和唯一性，修改后同步更新菜单显示和相关提示，不改变该 profile 的连接配置及端口映射。
- 地址支持 IPv4、IPv6 和域名；frps 业务连接端口与 Dashboard/API 管理端口分开配置。
- 新建 profile 向导中由用户手动输入 Dashboard/API 管理端口；输入为空时使用默认端口 `7500`，并提示：“请输入 Dashboard/API 管理端口（直接回车使用默认端口 7500）”。端口必须进行合法性和占用校验。
- 新建 profile 向导先完成服务端连接配置，端口映射由后续“修改当前 frps（服务端别名）端口映射”子菜单单独设置。
- 同时只有一个 active profile。
- 用户通过服务端编号选择 profile。服务端列表必须显示编号、名称、地址、端口、当前连接状态和映射数量，例如：`1. 生产服务器（192.0.2.10:7000）`。
- 切换 profile 时，如果 frpc 正在运行，必须提示并在用户确认后自动停止旧连接、切换配置并启动新服务端连接；程序必须等待连接检测结果，最多等待 30 秒，并明确显示“连接成功”或超时、认证失败、地址不可达等失败原因后返回菜单。如果 frpc 未运行，则只切换 active profile 配置。
- 删除 profile 前必须确认；删除 profile 时，同时删除该 profile 独立保存的端口映射配置；删除流程不要求额外自动生成备份。

### 8.3 映射管理

端口映射操作必须从 frpc 主菜单进入“修改当前 frps（服务端别名）端口映射”子菜单，再通过数字选择具体操作。主菜单不再将“新增端口映射”“查看当前服务端映射”“修改端口映射”“启用/停用端口映射”“删除端口映射”作为平级菜单项。

每个 profile 必须拥有独立的映射集合。切换服务端时，不得显示、修改或发送其他 profile 的映射。当前 active profile 的服务端别名必须显示在端口映射子菜单标题和状态区域中，防止用户误操作错误服务端。

端口映射子菜单固定包含以下功能：

1. 新增端口映射。
2. 查看当前服务端映射。
3. 修改端口映射。
4. 启用/停用端口映射。
5. 删除端口映射。
0. 返回 frpc 主菜单。

所有映射新增、修改、启用/停用和删除操作只能作用于当前 active profile；如果没有当前 active profile，应先引导用户选择或新建 frps 服务端。

首期支持：

- TCP
- UDP
- HTTP
- HTTPS

基础字段：

| 字段 | 说明 |
|---|---|
| 映射名称 | profile 内唯一，用于识别和修改 |
| 类型 | TCP、UDP、HTTP、HTTPS |
| 本地地址 | 默认 `127.0.0.1`，可由用户修改 |
| 本地端口 | 必填，校验范围和占用情况 |
| 远程端口 | TCP/UDP 使用；校验范围和冲突 |
| 域名 | HTTP/HTTPS 可选 |
| 启用状态 | 启用或停用 |
| 备注 | 可选 |

高级字段（首期预留配置模型，不强制全部提供菜单）：

- TLS
- HTTP Basic Auth
- 自定义请求头
- 健康检查
- 代理组和负载均衡
- 自定义插件参数

映射变更流程：

1. 用户在 frpc 主菜单确认当前 active profile 及其服务端别名。
2. 用户选择“修改当前 frps（服务端别名）端口映射”，进入专用数字子菜单。
3. 子菜单只加载该 profile 的映射。
4. 用户选择新增、查看、修改、启用/停用或删除映射。
5. 校验本地端口、远程端口、名称和字段组合。
6. 生成该 profile 独立的 frpc TOML 配置。
6. 对配置执行 frpc 校验或等价语法检查。
7. 备份旧配置并原子写入。
8. 如果客户端正在运行，提示立即重启或稍后生效。

## 9. 配置、目录与数据模型

### 9.1 推荐目录

Linux 示例：

```text
/usr/local/bin/frps
/usr/local/bin/frpc
/etc/frp-manager/
├── frps.toml
├── frpc.toml                 # 当前 active profile 生成文件
├── profiles/
│   ├── <profile-id>.toml     # 每个 frps 的独立 profile 与映射
│   └── <profile-id>.meta.toml
├── backups/
├── logs/
└── state.json
```

Windows 示例：

```text
C:\Program Files\frp-manager\
C:\ProgramData\frp-manager\
├── frps.toml 或 frpc.toml
├── profiles\
├── backups\
├── logs\
└── state.json
```

实际目录应允许用户自定义，但默认路径必须稳定，并在 `path` 菜单中显示。

### 9.2 数据隔离要求

- `profiles/<profile-id>` 是隔离边界。
- 每个 profile 独立保存服务端连接信息和映射集合。
- 运行时的 `frpc.toml` 由 active profile 生成，不直接让用户混合编辑多个 profile。
- 配置写入必须使用临时文件 + 校验 + 原子替换。
- 每次修改至少保留最近一次备份，建议按时间保留多份。
- 配置损坏时不得覆盖最后一份有效备份。

### 9.3 敏感信息

- token、Dashboard 密码、TLS 私钥不显示明文。
- Linux 使用权限控制；Windows 使用 ACL。
- 导出配置时默认剔除或脱敏敏感字段。
- 日志中不得打印 token、密码和私钥。
- 不把敏感信息写入命令行参数，避免被进程列表看到。

## 10. 服务管理与生命周期

### 10.1 Linux

- systemd：生成独立 service unit，支持 `start/stop/restart/status/enable/disable`。
- OpenRC：生成服务脚本并注册开机启动。
- 服务进程应使用专用低权限用户运行，除非用户明确选择其他方式。
- 日志优先接入 journald，同时可按配置写文件。
- 无 systemd/OpenRC 时提供后台进程兼容模式，并明确提示自启动能力受限。

### 10.2 Windows

- 注册 `frps` 或 `frpc` Windows Service。
- 服务启动失败时记录错误原因并提供日志路径。
- 支持服务启动类型：自动、手动、禁用。
- 卸载前停止服务并注销服务；配置和日志按用户选择保留或删除。

### 10.3 状态判断

状态不能只通过 PID 判断，应综合：

- 服务管理器状态。
- 进程是否存在。
- 配置是否可解析。
- frpc 与 frps 的实际连接状态（若可获取）。
- 最近退出码和最近错误日志。

---

## 11. 错误处理与用户提示

必须覆盖并给出可操作提示的场景：

- 不支持的操作系统或 CPU 架构。
- 下载失败、校验失败、网络超时。
- 没有管理员/root 权限。
- 端口被占用或端口值非法。
- 配置格式错误。
- token 错误或认证失败。
- TLS 配置不完整、证书不可读或证书过期。
- frps 不可达、DNS 失败、网络连接超时。
- Dashboard/API 不可用。
- 服务启动后立即退出。
- profile 或映射不存在。
- 删除 active profile 或运行中映射时的危险操作。
- 升级中断、回滚失败。

提示应包括：错误原因、影响、建议操作、日志路径；不能只显示无上下文的退出码。

## 12. 安全要求

1. 默认启用 token 引导，不允许用户在无确认的情况下使用完全开放认证。
2. TLS、Dashboard/API、监听公网地址均显示风险提示。
3. 管理密码和 token 输入时隐藏，输出时脱敏。
4. 所有配置文件采用最小权限。
5. 下载二进制时校验 HTTPS、文件完整性和版本来源。
6. 安装脚本不得覆盖用户已有配置，除非用户明确确认。
7. 卸载默认保留配置和日志，彻底删除需要二次确认。
8. 不在日志、错误信息、JSON 输出中泄露敏感信息。
9. 防止命令注入：用户输入不能未经校验直接拼接进 shell 命令、服务文件或配置文件。
10. 端口映射向公网开放前必须显示风险提示。

## 13. 非功能需求

### 13.1 可用性

- 首次安装向导应能在普通用户不阅读 frp 原生配置文档的情况下完成基础部署。
- 常用操作不超过 3 层菜单。
- 菜单支持中断和返回，不因输错一个字段退出整个程序。
- 所有重要变更可备份、可回滚。

### 13.2 可维护性

- Shell 与 PowerShell 逻辑应尽量共享配置模型和命令语义。
- 系统检测、下载、服务管理、配置生成、交互菜单、日志处理应模块化。
- 适配不同 frp 版本时不得把版本判断散落在所有脚本中。

### 13.3 可观测性

- 记录安装、升级、配置修改、启停、切换 profile 等审计事件。
- 日志支持按系统规范查看。
- 文件日志需要轮转或提供最大大小限制。
- `status` 和 `--json` 输出适合脚本采集。

## 15. 验收标准

### 15.1 安装验收

- 在每个目标 Linux 系统上能够识别系统和架构并完成正确二进制安装。
- systemd/OpenRC 环境下能够安装、启动、停止和设置开机启动。
- Windows x64 能通过 PowerShell 完成安装、注册服务、启动和卸载。
- 重复执行安装不会无提示覆盖已有配置。
- 网络失败和权限不足时有明确提示。

### 15.2 frps 验收

- `frps` 能显示运行状态、版本、路径和日志。
- 能完成启动、停止、重启、开机启动和卸载。
- 能配置 token、TLS 和 Dashboard/API。
- 能正确显示在线客户端和代理基本信息。
- Dashboard/API 不可用时提示真实原因。

### 15.3 frpc 验收

- 首次安装向导能创建一个有效 profile 并连接 frps。
- 能新增、编辑、删除和切换多个 profile。
- 每个 profile 的映射互不污染。
- 支持 TCP/UDP/HTTP/HTTPS 基础映射。
- 切换 profile 后生成正确的 active 配置并按提示重启。
- token、密码、TLS 私钥不会被明文展示或写入普通日志。

### 15.4 稳定性验收

- 配置输入错误时不破坏现有有效配置。
- 服务异常退出后可以通过菜单查看原因并恢复。
- 升级失败能恢复旧版本或给出明确人工恢复步骤。
- 卸载保留配置模式下，重新安装可以恢复原 profile 和映射。

## 17. 仍需在开发前最终确认的事项

以下问题不影响当前需求基线，但应在技术设计评审前确定：

1. **frp 版本技术验证**：业务上已确定首期固定 `v0.72.0`，开发前需要验证该版本的 TOML、命令行参数、认证机制和 Dashboard/API 字段。
2. **官方下载镜像**：是否仅使用 GitHub，是否需要国内镜像或自建 CDN。
3. **具体安装域名和脚本发布仓库**：用于替换示例 URL。
4. **frps Dashboard/API 的具体接口和认证方式**：需基于选定 frp 版本验证，避免将 Dashboard 登录凭据与 frpc token 混淆。
5. **用户名/密码的适用范围**：当前按 Dashboard 管理账号处理；如果要求用于 frpc 连接认证，需要确认采用 frp 哪种原生认证机制。
6. **HTTP/HTTPS 高级字段首期是否仅预留，还是进入首期菜单**。
7. **日志保留周期和最大磁盘占用**。
8. **是否允许自动修改 Linux 防火墙（ufw/firewalld）和 Windows 防火墙**。
9. **是否需要离线安装包和离线升级包**。
10. **项目名称、服务名称、配置目录名称和品牌标识**。

## 18. 需求结论

本项目首期应实现一个跨平台的 frp 管理封装：

- Linux 使用 Bash 安装和管理，Windows 使用 PowerShell 安装和 Windows Service 管理。
- `frps` 面向服务端生命周期、配置、安全和客户端连接信息管理。
- `frpc` 面向首次连接引导、多 frps profile 切换和独立端口映射管理。
- 以单 frpc 实例切换多个 frps profile 为首期模型；不同 profile 的映射严格隔离。
- 以中文交互菜单为主，同时提供稳定的非交互 CLI 和预留 JSON 输出。
- 以安全默认值、配置备份、原子写入和可回滚为基础质量要求。
