# 面板接管防火墙的兼容方案（讨论稿 v0.1）

> 背景：用户服务器安装了**宝塔面板**，防火墙由宝塔管理。frps 的端口自动开通功能
> 检测到 `ufw（运行中）`，但用户不确定宝塔的防火墙是接管系统还是自带，
> 也担心 frps 改防火墙会导致宝塔里已放行的规则丢失或冲突。
>
> 本文档先讲清底层机制，再给兼容方案，最后列出需要你确认的问题。
> **在确认前不改动防火墙相关的执行逻辑。**

---

## 1. 现象解释：为什么检测结果会误导

你截图里显示 `防火墙 ufw（运行中）`，这**技术上没有错**，但它不等于"防火墙由 ufw 管理"。

真实情况通常是：

```
宝塔面板「安全 → 防火墙」
        │  写入 SQLite（面板数据库）
        │  下发时直接调用 iptables
        ▼
   iptables（内核 netfilter）  ←── ufw 也在往这里写规则
        ▲
        │  ufw 自己的规则集
     ufw（如果系统装了并启用）
```

也就是说：**宝塔和 ufw 可能同时在同一张 iptables 表上写规则**。
我们的检测只看了"ufw 是否 active"，没看"谁在实际管理规则"，所以给了你一个有误导性的结论。

> 注意：宝塔面板的防火墙**不是自带的独立防火墙**，它是对系统 iptables 的**管理界面**。
> 所以你在宝塔里加的放行规则，本质是 iptables 规则。

## 2. 各面板的底层机制

| 面板 | 底层实现 | 规则存储 | 重载行为 | 与系统防火墙关系 |
|---|---|---|---|---|
| **宝塔 Linux**（BT Panel） | 直接调用 `iptables`（少数新版本在部分系统用 nftables） | 面板 SQLite（`/www/server/panel/data/db/firewall.db`） | 从数据库重新下发规则，**可能重建 INPUT 链** | 与 ufw/firewalld **并存时互相干扰** |
| **aaPanel**（宝塔国际版） | 同宝塔 | 同宝塔 | 同宝塔 | 同宝塔 |
| **小皮面板**（phpStudy/xp.cn） | `iptables`（部分版本 firewalld） | 面板配置 | 重新下发 | 同上 |
| **1Panel** | 抽象层：ufw / firewalld / iptables 三选一 | 依赖所选后端 | 调用后端重载 | 可能接管 ufw/firewalld |
| **cPanel / Plesk** | `firewalld` 或 `CSF` | 各自配置 | 各自重载 | 接管 firewalld |
| **宝塔 Windows** | Windows 防火墙（`netsh advfirewall`） | 面板数据库 | 重新下发 | 与系统防火墙同一套 |

**关键结论**：面板不是"另一种防火墙"，而是"防火墙的管理层"。
所以风险和冲突点在于：**两个管理层同时往同一套规则里写**。

## 3. 直接回答你的三个问题

### Q：宝塔接管的是系统防火墙，还是自带的？
**是接管系统防火墙**（iptables / Windows 防火墙）。宝塔自己没有独立的防火墙内核。

### Q：frps 开启防火墙或接管，会不会让宝塔里已放行的规则丢失？
分三种情况：

| frps 的动作 | 对宝塔规则的影响 | 风险 |
|---|---|---|
| 只**追加** iptables 规则（`-I INPUT`） | 不会删除宝塔规则，但**可能改变规则顺序**（放行提前或靠后） | 低 |
| 执行 `ufw --force enable` | ufw 会**重建自己的规则集**，可能与宝塔的 iptables 规则冲突 | **中高** |
| 执行 `firewall-cmd --reload` / 面板重载 | 各自从自己数据库重建，**对方的规则可能被清掉** | **高** |

**最危险的不是"立即丢失"，而是"静默失效"**：
- frps 加了规则 → 当时能用
- 之后你重载宝塔防火墙 → 宝塔重建 INPUT 链 → frps 的规则消失
- 端口又不通了，但 frps 状态页仍显示"已放行" → 你会被误导

### Q：会不会冲突？
**会**，尤其是你机器上 `ufw` 和宝塔同时在写 iptables 的情况。
冲突表现：规则被覆盖、端口时通时不通、面板里看到的和实际生效的不一致。

**所以：在面板接管的机器上，frps 不应该直接写系统防火墙。** 这是本方案的核心结论。

## 4. 兼容策略：分三层，按环境自动选择

### 第 0 层：只读 + 生成放行清单（**面板接管时的默认行为**）

- frps **不动任何防火墙规则**
- 只做两件事：
  1. 检测出"防火墙由面板 X 接管"
  2. 输出需要放行的端口清单，提示你去面板里加
- 好处：零风险、零冲突
- 代价：仍需手工操作（但比每次去面板找端口好——至少清单是自动生成的）

### 第 1 层：面板 API 集成（**推荐给宝塔/aaPanel**）

宝塔提供 HTTP API，可以在面板层面添加规则：

```
POST http://<面板地址>:<端口>/firewall?action=AddRule
参数：port=6000&ps=frp-auto&types=tcp
鉴权：request_time + request_token（由面板 API 密钥计算）
```

- 规则写进**面板数据库** → 宝塔重载时不会丢
- 不需要 root shell、不需要 SSH 凭据，只需要面板 API 密钥
- 风险：API 密钥是敏感凭据（但可随时在面板重置，且可限制来源 IP）

### 第 2 层：直写系统防火墙（**当前实现，仅用于无面板环境**）

仅在**没有检测到任何面板接管**时启用。

### 选择逻辑

```
检测到面板（宝塔/aaPanel/小皮/1Panel/cPanel/Plesk）
   ├ 配置了面板 API → 用第 1 层（API）
   └ 未配置 API    → 用第 0 层（只读 + 清单），并提示"可配置 API 自动完成"
未检测到面板
   └ 用第 2 层（直写系统防火墙）
```

## 5. 冲突检测与显性提示

### 5.1 多管理层检测

同时存在多个"防火墙管理层"时，状态页必须**显性标红**：

```
  防火墙       ⚠ 检测到多套防火墙管理层（可能冲突）
              - ufw：运行中（管理 iptables）
              - 宝塔面板：已安装（直接管理 iptables）
              建议：只保留一套管理方式，或在 frps 中使用只读/API 模式
```

检测方法：
- ufw active / firewalld running / iptables 有 DROP 策略 → 系统层管理层
- `/www/server/panel` 存在 + `bt` 服务 → 宝塔
- `/www/server/phpstudy` 或 xp 面板特征 → 小皮
- `/opt/1panel` → 1Panel
- `cpanel` / `plesk` 特征目录 → cPanel/Plesk
- 两者同时存在 → 判定为冲突

### 5.2 「规则被外部清除」检测（重要）

每次同步时，对已记录"已放行"的端口**复核是否仍然存在**：

- 存在 → 正常
- 不存在 → 标记 `lost`，告警：
  ```
  ⚠ 有 2 条规则已被外部清除（通常是面板重载防火墙覆盖）
    6000/tcp、6001/tcp 已不在防火墙中
    建议：改用面板 API 模式，或手动在面板中放行
  ```
- 写审计日志

这直接把"静默失效"变成"显性告警"。

### 5.3 启用前的强制确认

在检测到面板接管 + 用户仍选择"直写系统防火墙"时，
必须展示风险摘要并输入 `YES`：

```
检测到宝塔面板正在管理防火墙（iptables）。
frps 直接写入规则可能：
  1) 改变规则顺序
  2) 在宝塔重载防火墙后被覆盖而静默失效
建议改用：只读清单模式 / 面板 API 模式
仍要直写系统防火墙？请输入 YES：
```

## 7. 宝塔 API 集成设计（第 1 层）

### 7.1 配置

```toml
# /etc/frp/auto-port.toml
[panel]
type = "baota"                 # baota | aapanel | none
url = "http://127.0.0.1:8888"
api_key = "***"                # 面板「设置 → API 接口」里的接口密钥
verify_tls = false
```

> API 密钥属于敏感凭据，写入 `auto-port.toml` 后保持 0600；
> 也可改用环境变量 `FRP_PANEL_API_KEY` 避免落盘。

### 7.2 调用

```
request_time = 当前时间戳
request_token = md5(request_time + md5(api_key))
POST {url}/firewall?action=AddRule
     request_time=...&request_token=...&port=6000&ps=frp-simple-bash&types=tcp
```

- 添加：`action=AddRule`
- 删除：`action=DelRule`（参数同）
- 查询：`action=GetRules`（可选，用于复核是否生效）

> ⚠️ 不同宝塔版本参数名可能略有差异，需要在你的面板上实测确认。

### 7.3 安全约束

- API 密钥只存本地 0600，不写日志
- 面板 API 通常要求「IP 白名单」，建议只允许 `127.0.0.1`（frps 与本机面板同机）
- 调用失败不重试超过 1 次，避免面板侧限流
- 所有 API 调用写审计（不含密钥）

## 13. 宝塔 API 集成（P5，v1.0.0-rc.12 已完成）

### 13.1 为什么用 API 而不是直写 iptables

| 方式 | 规则存放位置 | 宝塔重载后 | 结论 |
|---|---|---|---|
| 直写 iptables | 仅内核规则表 | **被面板覆盖丢失** | ❌ |
| 面板 API | **面板数据库** | 面板重新下发，依然存在 | ✅ |

### 13.2 配置

菜单：`frps` → `6) 端口自动开通` → `13) 面板 API 配置（宝塔 / aaPanel）`

子菜单支持：测试连接、设置 API 地址、设置 API 密钥、切换面板类型、切换 TLS 校验、清空配置。
密钥输入使用不回显输入，写入 `/etc/frp/auto-port.toml`（0600）。

配置文件形态：

```toml
panel_mode = "auto"          # auto | readonly | panel-api | direct

[panel]
type = "baota"               # baota | aapanel
url = "http://127.0.0.1:8888"
api_key = "***"              # 也可用环境变量 FRP_PANEL_API_KEY，避免落盘
verify_tls = false
timeout = 10
list_action = "GetRules"
add_action = "AddRule"
del_action = "DelRule"
```

### 13.3 鉴权与调用

```
request_time  = 当前时间戳（秒）
request_token = md5(request_time + md5(api_key))
POST {url}/firewall?action=AddRule
     request_time=...&request_token=...&port=6000&types=tcp&ps=frp-simple-bash-auto
```

- 添加规则带备注 `frp-simple-bash-auto`，便于识别与清理
- 删除时先 `GetRules` 查规则 ID，再 `DelRule`
- 失败只重试 0 次，避免面板限流
- 所有调用写审计，**不记录密钥**

### 13.4 模式判定（最终）

```
auto-port.toml 的 panel_mode
  ├ "direct"     → 直写系统防火墙（仅无面板机器）
  ├ "readonly"   → 只生成清单
  ├ "panel-api"  → 走面板 API
  └ "auto"（默认）
        ├ 面板 API 已配置(地址+密钥) → panel-api
        ├ 检测到面板但未配置 API       → readonly
        └ 无面板                      → direct
```

菜单状态页会直接显示当前工作模式，例如：
`工作模式  面板 API（推荐）`

### 13.5 使用步骤

1. 宝塔面板 → 设置 → API 接口 → 开启，复制「接口密钥」
   （建议同时把 API 白名单限制为 `127.0.0.1`）
2. `frps` → `6) 端口自动开通` → `13) 面板 API 配置`
3. 依次设置：`2) API 地址` → `3) API 密钥`
4. `1) 测试连接` 应显示"当前有 N 条防火墙规则"
5. 回到主菜单：`5) 启用自动放行` → `2) 预览` → `3) 同步`

此后所有放行规则写入宝塔数据库，**宝塔重载/重启都不会丢**。

### 13.6 参数名不确定时的校准方法

不同宝塔版本参数名可能略有差异。若「测试连接」失败：

1. 先确认面板「设置 → API 接口」已开启，且调用来源 IP 在白名单内
2. 若返回参数错误，可在 `auto-port.toml` 的 `[panel]` 中调整
   `list_action` / `add_action` / `del_action` 三个动作名
3. 错误信息会带上面板原始返回（截断 200 字符），便于定位

> 注：本文档的 API 参数基于宝塔通用规范，**首次使用请务必先跑「测试连接」**，
> 确认无误后再启用自动放行。

## 14. 紧急修复：防火墙启用导致服务失联（v1.0.0-rc.13）

### 14.1 事故复盘

现象：frpc 日志持续 `connect to server error: dial tcp ...:7000: i/o timeout`，
7000 端口不通。

根因（本项目缺陷，三条同时存在）：

| 缺陷 | 后果 |
|---|---|
| `firewall_enable` 启用前**不保存快照** | 启用后无法回滚，只能手工修 |
| 面板接管时**只是文本警告**，用户按 YES 仍可继续 | `ufw --force enable` 重建规则链，覆盖宝塔已放行端口 |
| 启用后**不校验** frps 业务端口是否真的放行 | 失联没有任何告警 |

关键机制：`ufw --force enable` 会把 ufw 自己的规则集插入 iptables，
宝塔此前直接下发的规则可能被挤到后面或被覆盖 → 7000 被 DROP → frpc 超时。

### 14.2 修复内容

1. **面板接管时硬阻止**：`firewall_enable` 检测到面板直接抛错，**一条命令都不执行**。
   确需接管必须 `--force`（风险自负）。
2. **启用前强制快照**：保存 `iptables-save` / `nft list ruleset` / `ufw status`
   到 `/etc/frp/firewall-snapshot.json`（0600），作为回滚依据。
3. **启用后自检**：复查 frps 业务端口是否在放行集合中，缺失即当场告警。
4. **一键回滚**：`frps ports firewall revert`（或菜单 `14) 回滚防火墙到快照`）
   - 若快照显示 ufw 原本关闭 → 先 `ufw disable`（最常见解药）
   - 再 `iptables-restore` 恢复规则
5. **菜单新增「急救与回滚」组**：
   ```
   13) 保存防火墙快照
   14) 回滚防火墙到快照（急救）
   15) 面板 API 配置（宝塔 / aaPanel）
   16) 撤销全部自动放行并关闭
   ```

### 14.3 失联后的恢复步骤（用户视角）

```bash
# ① 判断是谁在挡
sudo ufw status verbose
sudo iptables -S INPUT | head -20
sudo ss -lntp | grep 7000

# ② 快速验证：临时关 ufw
sudo ufw disable
#    若 frpc 立刻恢复 → 确认是 ufw 覆盖

# ③ 用本工具回滚（推荐）
sudo frps ports firewall revert --yes

# ④ 或手工补放行
sudo ufw allow 7000/tcp && sudo ufw reload
```

### 14.4 结论：面板机器上应该怎么做

**不要用「一键启用系统防火墙」**。正确路径：

1. 菜单 `15) 面板 API 配置` → 填宝塔 API 地址与密钥 → `1) 测试连接`
2. 菜单 `5) 启用自动放行`（此时模式自动变为 `panel-api`）
3. 规则写进宝塔数据库，面板重载不丢，也不会动系统防火墙

若暂时不想配 API，就用默认的 `readonly` 模式：本工具只列出待放行端口，
由你在宝塔里手工添加，零风险。
