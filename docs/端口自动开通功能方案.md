## 2. 关键事实核对（先对齐，避免做无用功）

### 2.1 frp 本身**已经会**自动监听 remote_port

frp 的工作机制就是：frpc 注册一个 proxy（带 `remotePort`），frps 收到注册后**自动 bind 该端口并监听**。这一步**不需要任何额外配置**，也不是本项目要补的能力。

证据：
- 本项目 `render()` 只负责把映射写进 `frpc.toml` 的 `remotePort`，frps 侧无需任何改动
- 你现在能通过映射端口 SSH 登录内网，本身就是 frps 已自动监听该端口的证明

**所以「frps 开放端口监听」这件事，frp 已经做完了。**

### 2.1.1 一个外部请求要过的 4 道关

```
外部用户
   │
   ▼ ① 云厂商安全组   ← 在服务器"外面"，本机看不到也改不了
   ▼ ② 主机网卡 / NAT
   ▼ ③ 操作系统防火墙  ← 本机能改（ufw / firewalld / iptables）
   ▼ ④ frps 进程监听   ← frp 自动完成，已通
frpc → 内网服务
```

类比：④=店门开了，③=小区门卫，①=城市高速入口。
frp 只负责开"店门"，**卡住的通常是 ① 或 ③**。

### 2.1.2 如何判断卡在哪一关

在 frps 服务器上：

```bash
# 关卡④：frps 是否真的在监听
sudo ss -lntp | grep -E ':(6000|7000)'
# 关卡③：系统防火墙是否放行
sudo ufw status || sudo firewall-cmd --list-all || sudo iptables -S | head -20
```

连通性测试：

| 测试 | 结果含义 |
|---|---|
| 内网 `nc -vz 内网IP 6000` 通 | ②③ 没问题 → 卡在 **①安全组** |
| 内网不通、本机 127.0.0.1 通 | 卡在 **③系统防火墙** |
| 公网 `nc -vz 公网IP 6000` 通 | 全通，不需要本功能 |

### 2.2 真正挡住外部访问的是这三层

| 层 | 位置 | 现状 | 谁来开 |
|---|---|---|---|
| ① frps `allowPorts` 白名单 | frps 配置里 | 本项目**未管理**；不配置=全放行 | 写 frps.toml + 重启 |
| ② 操作系统防火墙 | 服务器本机 | 本项目只做**检测提示**（`firewall_hint`），**不改规则** | ufw / firewalld / iptables |
| ③ 云厂商安全组 | 腾讯云/Aliyun 控制台 | 在 OS 之外，本机看不到也改不了 | 控制台手工 or 云 API |

> 你截图里的服务器名是 `tencent-4h4g-134`，大概率是腾讯云轻量/云服务器。
> 国内云主机最常见的卡点其实是 **③ 安全组**，而不是 ② 系统防火墙。

### 2.3 本项目当前立场

README 明确写着：「防火墙规则始终由用户管理，本项目不自动修改」。
这个新功能等于**推翻这条设计原则**，需要你明确授权。

## 3. 三种实现路线

### 路线 A：服务端被动同步（frps 自己看 frpc 注册了什么）

**原理**：frp 协议本身已经把 `remote_port` 从客户端传到了服务端。frps 侧管理器读本机 Dashboard API 的 `proxies` 列表，拿到所有在线的 remote_port，然后：
- 与本机防火墙现有规则做 diff
- 自动放行缺失的端口、回收已消失的端口

**优点**
- 不需要新协议、不需要客户端持有任何凭据
- 不新增攻击面（数据源就是 frp 自己的管理 API）
- 实现最小，风险最低

**缺点**
- 只解决第 ② 层（OS 防火墙），**解决不了云安全组**
- 有秒级窗口：frpc 注册成功 → 管理器下一次同步才放行
- 仍受第 ① 层 allowPorts 约束（那是 frp 自己的策略，不该绕过）

---

### 路线 B：客户端主动请求 —— SSH 推送

**原理**：frpc 侧在添加映射时，SSH 到 frps 主机执行 `frps ports allow 6000 --proto tcp`。

**优点**：实时、可实现「服务端审批」流程。

**缺点（致命）**
- 客户端必须持有**服务器 SSH 凭据**（密钥或密码）→ 这是把服务器 root 权限散落到每台内网机器
- 方向反直觉：通常只允许服务器连内网，不允许内网反连服务器
- 一旦某台内网机器被入侵，攻击者直接获得 frps 主机 shell

> 除非你有「所有客户端都可信且同属一个安全域」的强假设，否则**不建议**。

---

### 路线 C：客户端主动请求 —— 服务端受控 API

**原理**：frps 侧跑一个常驻 agent（监听 `127.0.0.1:7800` 或专用端口），提供 `POST /ports` 接口，要求 HMAC 签名 + TLS。frpc 侧添加映射后调用它。

**优点**
- 协议干净、可审计、可限流、可审批
- 不需要 SSH 凭据，凭据是「一次性 token」

**缺点**
- 新增一个守护进程（要写、要部署、要保活、要升级）
- **鸡生蛋问题**：agent 自己要监听的端口，必须先手工开通（安全组+防火墙）一次
- 证书/密钥分发与轮换
- 攻击面从「frp 协议」扩大到「一个能改防火墙的 HTTP 服务」

---

### 三条路线对比

| 维度 | A 被动同步 | B SSH 推送 | C 受控 API |
|---|---|---|---|
| 解决 OS 防火墙 | ✅ | ✅ | ✅ |
| 解决云安全组 | ❌（需另接云 API） | ⚠️（同左） | ⚠️（同左） |
| 新增攻击面 | 几乎为零 | 高（SSH 凭据外流） | 中（新守护进程） |
| 客户端要凭据 | 不要 | 要（危险） | 要（受控 token） |
| 实现成本 | 低 | 中 | 高 |
| 实时性 | 秒级 | 实时 | 实时 |
| 与 frp 协议重复 | 否（复用） | 是（重复传端口） | 是（重复传端口） |

## 3.5 关键策略：安全组「一次性开区间」

云厂商安全组支持**按端口区间**放行（如 `6000-6999`），不必逐个端口添加。

因此对**不提供云 API 密钥**的场景，最省事且最安全的组合是：

| 层 | 谁负责 | 频率 |
|---|---|---|
| ① 云安全组 | **用户手工开一次区间** | 一次性 |
| ③ 系统防火墙 | **本项目自动跟随 frp 实际映射** | 全自动 |
| ④ frps 监听 | frp 自带 | 全自动 |

这样既实现"以后不用每次去开端口"，又不需要把云账号密钥交给本工具。

**云 API 自动化（三期）在本场景下属于不必要的复杂度，建议不做。**

## 4. 推荐方案：分三期，一期先做路线 A

### 一期：OS 防火墙自动跟随（路线 A）
- frps 侧管理器读取 Dashboard API 的实际 proxy 列表
- 只放行**确实已注册**的端口（不信任客户端"声明"，只信任 frp 已确认的结果）
- 默认 `dry_run = true`：先只报告「建议放行哪些端口」，你确认后再开真执行
- 规则打标记（iptables comment / firewalld rich rule），便于精确回收
- 删除映射或客户端离线超过 TTL → 自动回收

### 二期：allowPorts 白名单自动维护（可选）
- 自动把已注册端口并入 frps 的 `allowPorts`
- 需要改 frps.toml + 重启/重载，风险比防火墙大
- 建议：只在你**主动启用** allowPorts 限制时才有意义

### 三期：云安全组（需你授权）
- 腾讯云/Aliyun API 需要 SecretId/SecretKey
- 这是极高敏感凭据，且最小权限策略复杂
- 建议先确认你确实需要，再单独设计

## 5. 安全模型（这是决定做不做的关键）

### 5.1 谁能触发放行？

| 方案 | 触发者 | 风险 |
|---|---|---|
| A | 任何能连接 frps 的客户端（通过注册 proxy） | 恶意客户端可注册任意端口 → 防火墙被逐个打开 |
| B/C | 持有 token/SSH 的客户端 | 凭据泄露即失控 |

**必须有的护栏（无论哪个方案）**：
1. **端口范围白名单**：只允许放行指定区间（如 6000-6999），范围外拒绝
2. **禁止特权端口**：`< 1024` 一律拒绝
3. **单客户端配额**：每个 clientID 最多 N 个端口（防一次开 1-65535）
4. **速率限制**：单位时间内最多新增 M 条规则
5. **allowPorts 仍是权威**：防火墙跟随 allowPorts，不能反过来放宽 allowPorts
6. **审计日志**：记录 谁/何时/开了哪个端口/结果
7. **默认 dry-run**：首次启用只观察不执行

### 5.2 最坏情况推演

- 恶意客户端注册 6000-6999 全部端口 → 配额 + 速率限制把它限制在 N 个
- 端口冲突：两个客户端抢同一 remote_port → frp 自身会拒绝后注册者；管理器按 frp 实际结果放行，不会误开
- 管理器被攻破 → 它只能改防火墙，不能执行任意命令（实现上禁止 shell 拼接，全部参数化调用）

### 5.3 一个反直觉但重要的点

**"客户端申请什么就开什么"本身是危险的**。
更安全的语义是：**"frps 已经接受的注册，就保证外部可达"**——即放行集合由 frps 的实际状态决定，而不是由客户端的请求决定。这正是路线 A 的价值。

## 6. 一期详细流程（时序）

```
[frpc 添加映射]
   │ 写 mappings.toml + 重新 render frpc.toml
   ▼
[frpc 重启生效] ──注册 proxy(remotePort=6000)──▶ [frps]
                                                  │ 自动 bind 6000 监听
                                                  ▼
                                        [Dashboard API: proxies[].remotePort=6000, status=online]
                                                  │
[frps 侧管理器 · 定时/触发同步] ◀──────────────────┘
   │ 1. 拉取 proxies 列表 → 得到 {tcp:6000, tcp:6001}
   │ 2. 拉取当前防火墙放行集合 → 得到 {tcp:6000}
   │ 3. diff = {6000 保留, 6001 新增}
   │ 4. 校验：区间/特权端口/配额/速率
   │ 5. dry_run ? 输出计划 : 执行放行
   ▼
[结果] 审计日志 + 菜单可见「已自动放行 6001」
```

撤销流程对称：proxy 消失（删映射/客户端离线超 TTL）→ 下一次同步回收规则。

## 7. 配置项设计（草案）

```toml
# /etc/frp/auto-port.toml
enabled = false                  # 默认关闭，需显式开启
mode = "firewall"                # firewall | firewall+allowports
dry_run = true                   # 首次启用默认只报告不执行

# 允许放行的端口区间（必填，空 = 禁止一切）
port_ranges = [
  { start = 6000, end = 6999 },
]

deny_privileged = true           # 拒绝 < 1024
max_ports_per_client = 20        # 单客户端配额
sync_interval_seconds = 15       # 同步周期
prune_after_seconds = 120        # proxy 消失多久后回收规则

# 允许哪些 clientID（空 = 不允许任何客户端，需显式登记）
allow_clients = []
```

## 8. 命令与菜单（草案）

```
frps ports status        # 当前映射端口 + 防火墙状态（只读）
frps ports plan          # 打印 diff 计划（dry-run）
frps ports apply [--yes] # 立即同步一次
frps ports rules         # 列出本管理器添加的防火墙规则
frps ports revert --yes  # 撤销所有本管理器添加的规则
```

菜单：`frps 主菜单 → 服务端管理 → 端口自动开通`

## 9. 失败与回滚

| 场景 | 处理 |
|---|---|
| 防火墙命令失败 | 记日志、不中断 frps、下次重试；不影响已注册映射 |
| 规则与实际不一致 | 以 frps 实际 proxy 列表为准，重算后修复 |
| 管理器崩溃 | 已加规则**保留**（不自动清空，避免误伤），下次启动重新对账 |
| 用户手动加了冲突规则 | 只回收带本项目标记的规则，绝不删用户自己的 |
| 需要完全还原 | `frps ports revert` 按标记精确删除 |

规则持久化：iptables 用 `iptables-save`；ufw/firewalld 用其自身的持久化机制。

## 10.6 不限制区间的风险推演与护栏（v0.3 新增）

### 决策记录
- Q3：**不限制端口区间**
- Q3b：保留手填 remote_port（不做自动分配）
- Q3c：**开启即自动执行**（不强制 dry-run）

### 风险推演

若某台内网客户端被入侵，攻击者可：

1. 在 frpc 配置写入 `remote_port = 3306 / 6379 / 9200 / 任意`
2. frpc 注册 → frps 自动监听 → 管理器自动放行防火墙
3. 攻击者立即获得这些端口的公网入口

结果：服务器从「只开 7000 + 既有映射端口」变成「攻击者想开什么就开什么」。
本项目等于把防火墙变成了攻击者的端口开放器。

### 与安全组的矛盾

云安全组只能手工配置（无 API 密钥）：

| 端口策略 | 安全组需要 | 后果 |
|---|---|---|
| 不限制区间 | 全端口放行 | 安全组失效，系统防火墙成唯一防线 |
| 限定区间 | 一次性开该区间 | 安全组仍是有效防线，且只手工操作一次 |

**结论：不限制区间会让云安全组这道防线失效。** 这是本方案最大的安全代价，
需要用户明确接受。

### 强制护栏（不限制区间时必须全部启用）

| 护栏 | 作用 | 默认值 |
|---|---|---|
| `allow_clients` clientID 白名单 | 只有登记过的客户端才能触发放行 | 空 = 拒绝一切 |
| `max_ports_per_client` | 单客户端最多放行端口数 | 20 |
| `deny_privileged` | 拒绝 < 1024 端口 | true |
| 端口占用检查 | 已被系统进程占用的端口不放行 | 强制 |
| `sync_interval_seconds` | 同步周期 | 15 |
| 审计日志 | 谁/何时/放了哪个端口/结果 | 强制 |
| `frps ports revert` | 一键撤销本项目添加的全部规则 | 强制 |

启用该功能时，菜单必须展示上述风险摘要并要求输入 `YES`。

### 残余风险（明确记录）

即使启用全部护栏，仍存在：
- 已登记客户端被完全控制后，可占用其配额内的端口（如 20 个任意端口）
- 若安全组已全开，这些端口将直接暴露公网
- 本工具无法区分「正常映射」与「恶意映射」

因此：**不限制区间 + 安全组全开 + 客户端不完全可信 = 不建议开启此功能。**
建议至少保留「禁止特权端口」与「clientID 白名单」两项。

## 11. 待你确认的问题

### Q1. 「开放端口」具体指哪一层？
- (a) 只做**操作系统防火墙**（ufw/firewalld/iptables）—— 一期推荐范围
- (b) 还要做 **frps `allowPorts` 白名单**自动维护
- (c) 还要做**云厂商安全组**（需要云 API 密钥，安全评估另议）
- (d) 全都要

### Q2. 你更认可哪种触发方式？
- (a) **路线 A**：服务端自己看 frpc 注册了什么就放行什么（不要客户端凭据，推荐）
- (b) 路线 C：服务端跑受控 API，客户端带 token 请求
- (c) 路线 B：客户端 SSH 到服务器执行
- (d) 你原本设想的"客户端发送端口"具体是怎么发的？能描述一下预期的交互吗

### Q3. 放行范围怎么定？
- (a) 固定区间（如只允许 6000-6999）
- (b) 按 clientID 分配区间
- (c) 不限区间，但限制单客户端数量
- (d) 每次都要你在服务端手动批准

### Q4. 删除映射 / 客户端离线后，是否自动回收端口？
- (a) 自动回收（推荐，避免规则堆积）

## 16. 防火墙后端实现（多发行版兼容）

### 16.1 探测矩阵

不同发行版默认防火墙不同，探测按"**谁真正在生效**"决定，而不是"谁装了"：

| 优先级 | 后端 | 生效判定 | 典型发行版 |
|---|---|---|---|
| 1 | ufw | `ufw status` 含 `Status: active` | Debian / Ubuntu |
| 2 | firewalld | `firewall-cmd --state` = `running` | RHEL / CentOS / Rocky / Alma / Fedora / openSUSE |
| 3 | iptables | `iptables -S` 中 `-P INPUT DROP/REJECT` | Alpine / Arch / 老系统 / 容器 |
| 4 | nftables | `nft list ruleset` 含 `hook input` + `policy drop` | 新 Arch / Alpine / 纯 nft 系统 |
| 5 | Windows | `netsh advfirewall show allprofiles state` 含 `ON` | Windows Server |

**关键修正**：安装顺序不等于生效顺序。例如 firewalld 装了但没启动、而 iptables 有
`-P INPUT DROP` 时，旧实现会误判为"无防火墙"；新实现会正确选中 iptables。

### 16.2 各后端操作

| 后端 | 放行 | 回收 | 持久化 |
|---|---|---|---|
| ufw | `ufw allow 6000/tcp` | `ufw delete allow 6000/tcp` | ufw 自身 |
| firewalld | `firewall-cmd --permanent --add-port=6000/tcp` + `--reload` | `--remove-port` + `--reload` | `--permanent` |
| iptables | `iptables -I INPUT ... -m comment --comment frp-simple-bash:auto` | `-D`（按 comment 匹配） | `iptables-save` → `/etc/iptables/rules.v4` |
| nftables | `nft add rule inet filter input tcp dport 6000 accept` | `nft delete rule ...` | 需写入 `/etc/nftables.conf`（给出指引） |
| Windows | `netsh advfirewall firewall add rule name=frp-simple-bash-auto-tcp-6000 ...` | 按同名删除 | 系统持久 |

**所有命令均为参数列表调用，绝不拼接 shell 字符串。**

### 16.3 「防火墙未启用」的处理

按发行版推荐管理器（`preferred_firewall()`）：

| 发行版族 | 推荐 |
|---|---|
| Debian / Ubuntu | ufw |
| RHEL 系 / SUSE | firewalld |
| Alpine / Arch / 其他 | nftables |

提供三级处理：

1. **检测**：`frps ports firewall status` 打印发行版、推荐管理器、各管理器状态
   （`active` / `installed` / `missing`）
2. **计划**：`frps ports firewall plan` 打印将要执行的完整命令（安装/放行/启用）
3. **一键启用**：`frps ports firewall enable`

### 16.4 一键启用的安全顺序（防自锁）

启用防火墙最容易造成的严重事故是**把用户自己的 SSH 锁在门外**。
因此执行顺序被硬编码为：

```
① 探测 SSH 实际监听端口（ss -lntp 找 sshd；退化到 /etc/ssh/sshd_config）
   ↳ 探测不到 → 直接拒绝自动启用（不允许猜 22）
② 放行 SSH 端口
   ↳ 任一条失败 → 立即中止，且此时防火墙尚未启用，安全
③ 放行 frps 自身端口（bindPort / vhost / kcp / quic / 对外 Dashboard）
   以及本工具已放行的映射端口
④ 最后才启用防火墙（ufw --force enable / systemctl enable --now firewalld）
⑤ 复查 firewall_detect() 确认 active，写审计
```

### 16.5 未启用时同步的行为

`ports_sync(apply=True)` 在防火墙未启用时**拒绝执行并报错**，错误信息包含
发行版与具体引导（而不是静默成功）：

```
系统防火墙未启用，拒绝自动放行端口。
  发行版：debian
  已安装 ufw 但均未启用，可执行 `frps ports firewall enable`
```

这样不会出现"以为开了其实没开"的假象。

## 17. 同步算法

```
1. 前置检查 C1-C3（C4 在启用时检查一次）
2. 读 /etc/frp/auto-port.toml；enabled=false 直接返回
3. GET frps Dashboard /api/v2/proxies?page=N （分页）
   过滤：status.phase == "online" 且 spec.type ∈ {tcp, udp}
   提取 (remotePort, type, clientID, name)
4. 过滤：clientID ∈ allow_clients
5. 过滤：deny_ports_enabled 时排除 deny_ports 中的端口（命中则跳过并记审计）
6. 过滤：端口冲突检查（ss/lsof 查看是否被非 frps 进程占用）
   —— frps 自己占用的端口要排除在外（通过 frps 的 PID 判断）
7. 按 clientID 分组，应用 max_ports_per_client（超出则保留最早的，其余告警）
8. desired = 过滤后的集合
   current  = ports-state.json 中 opened 集合
   to_add   = desired - current
   to_del   = current - desired  （且该 proxy 已消失超过 prune_after_seconds）
9. 逐条执行 to_del → to_add，每条写审计
10. 更新 ports-state.json（原子写）
```

  且 SSH 端口探测失败时直接拒绝
- **第 13 项双重语义**：撤销规则的同时关闭自动放行，否则定时器会在 15 秒后重新放行
